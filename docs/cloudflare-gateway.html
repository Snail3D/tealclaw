TealClaw ↔ OpenClaw via Cloudflare Tunnel (Gateway Setup)

This page is a tight, repeatable recipe for exposing an OpenClaw Gateway to a TealClaw client over the internet using a Cloudflare Tunnel (stable hostname, no port-forwarding). It also documents the main “kinks” we’ve hit so the next setup takes minutes, not hours.

Security model: TealClaw is a client-side PWA. Your TealClaw browser talks to your OpenClaw Gateway over HTTPS/WebSocket. Keep your gateway token secret and use Cloudflare access controls when appropriate.

0) Prereqs

  • You control a Cloudflare zone (e.g. example.com)
  • You can run cloudflared on the machine hosting the OpenClaw Gateway
  • Your OpenClaw Gateway is running locally (usually on http://localhost:18789)

1) Make sure the Gateway is reachable locally

On the gateway host:

openclaw status
# and/or
curl -sS http://127.0.0.1:18789/health || true
Common failure: Gateway is bound only to 127.0.0.1 but you expect LAN/Tunnel access. Fix by binding to 0.0.0.0 in your OpenClaw config (then restart). If you only ever access via the same machine + tunnel, loopback can still be OK — just be consistent.

2) Create a named Cloudflare Tunnel (stable)

Use a named tunnel so your hostname is stable (no “quick tunnel” URLs).

# Authenticate this host with your CF account
cloudflared tunnel login

# Create a named tunnel
cloudflared tunnel create <TUNNEL_NAME>

# Route DNS hostname → tunnel
cloudflared tunnel route dns <TUNNEL_NAME> <GW_HOSTNAME>
# example: cloudflared tunnel route dns openclaw-gw gw.example.com

3) Point the tunnel at the local Gateway

Create (or edit) your cloudflared config. Locations vary; common ones are:

  • ~/.cloudflared/config.yml
  • /etc/cloudflared/config.yml (Linux service installs)

Example config.yml (use your real tunnel UUID and credentials file path):

tunnel: <TUNNEL_UUID>
credentials-file: /path/to/<TUNNEL_UUID>.json

ingress:
  - hostname: <GW_HOSTNAME>
    service: http://localhost:18789
  - service: http_status:404

Run it:

cloudflared tunnel run <TUNNEL_NAME>

4) TealClaw config: point agent URL at your hostname

In TealClaw, set your agent URL to the tunnel hostname. Example JSON config block (placeholders — do not paste real secrets into docs):

{
  "mode": "agent",
  "agents": [
    {
      "id": "home",
      "name": "Home",
      "url": "https://<GW_HOSTNAME>",
      "token": "<OPENCLAW_GATEWAY_TOKEN>",
      "active": true
    }
  ]
}
Tip: If you also use Groq Whisper/TTS in TealClaw, those keys live in browser localStorage. The gateway token also lives in localStorage. TealClaw does not run a backend.

5) Troubleshooting (fast)

A) “It was fine until I pasted the wrong key”

  • Re-paste the correct key/token in a TealClaw JSON block
  • If the UI is weird after changes, unregister the service worker (below)

B) Infinite queue / stuck “sending” / agent never responds

  • Confirm tunnel is up and DNS hostname resolves to Cloudflare
  • Confirm gateway is healthy locally (curl http://localhost:18789/health)
  • Check for a WebSocket handshake failure (DevTools → Network → WS)
  • Validate the agent URL is https://... (not http://)

C) Changes “didn’t apply” (Service Worker caching)

  • Hard refresh (Shift-Reload)
  • DevTools → Application → Service Workers → Unregister

D) Gateway reachable locally, not reachable remotely

  • Confirm your tunnel is pointing to the right local port
  • If you intended LAN access without tunnel, bind gateway to 0.0.0.0

Keep it tight: named tunnel → stable hostname → ingress to local gateway → TealClaw agent URL points to that hostname. The rest is debugging keys, binding, and caching.
